# Palette Kit v0.4 — Level Axis Specification

## Purpose

This document formalizes the **Level axis** in Palette Kit v0.4.

The Level axis defines **relative depth and elevation** within a perceptual scale.
It exists to make spatial hierarchy explicit and declarative, without relying on inference
or hidden heuristics.

The Level axis answers a single question:

> **At what relative depth or elevation does this color live within its usage context?**

---

## Core Principle

**Level is never inferred.**

If a color participates in a perceptual scale (such as a Radix-like scale),
its position in that scale must be provided explicitly.

Implicit step inference leads to:

- unpredictable behavior
- invisible coupling between components
- undocumented visual rules
- long-term design drift

Palette Kit avoids this by treating Level as a **first-class orthogonal axis**.

---

## What Level Is (and Is Not)

### Level IS

- an ordinal position in a perceptual scale
- a representation of spatial depth or elevation
- an explicit input to the resolver
- interpreted differently by each usage strategy

### Level IS NOT

- semantic intent
- interaction state
- visual emphasis
- contrast direction
- a substitute for hierarchy or importance

---

## Canonical Level Range

Palette Kit adopts a **Radix-compatible ordinal range**:

```ts
export type Level = 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 | 9
```

This range is:

- ordered (1 < 2 < ... < 9)
- usage-agnostic at the type level
- semantically interpreted per usage strategy

The exact perceptual mapping of each level is the responsibility of the resolver.

---

## Relationship to Other Axes

The Level axis is fully orthogonal to existing axes.

| Axis | Question Answered |
| ---- | ---- |
| Usage | Where is the color applied? |
| Intent | Why does this color exist? |
| Relation (on \| over \| under) | How does it relate to another surface? |
| Level | At what depth/elevation? |
| State | When is this color used? |
| Context | In which environment is it resolved? |

No axis subsumes another.

---

## Usage-Specific Interpretation

The same Level value has **different physical meaning** depending on usage.

This is intentional and required.

---

### Fill

For `fill`, Level represents **surface depth**.

Examples:

- Level 1 → base background surface
- Level 2–3 → raised surfaces (cards, panels)
- Level 4–6 → interactive fills (buttons, controls)
- Level 7+ → strong emphasis surfaces

Interpretation characteristics:

- primarily affects luminance
- chroma may increase with higher levels
- no contrast guarantees are implied

---

### Lines

For `lines`, Level represents **structural prominence**.

Examples:

- Level 1 → hairline dividers
- Level 2–3 → default borders
- Level 4–5 → emphasized outlines
- Level 6+ → rare, strong separators

Interpretation characteristics:

- chroma is constrained
- luminance shifts are subtle
- alpha may be used

---

### Visual Vocabulary

For `visualVocabulary`, Level is **not applicable**.

Text, icons, and glyphs do not participate in spatial depth scales.

Attempting to use Level with this usage is considered a type error.

Contrast and legibility are resolved exclusively via the `on` relation.

---

### Overlays

For `overlays`, Level represents **overlay strength**, not depth.

Examples:

- Level 1–2 → subtle hover overlays
- Level 3–4 → pressed or selected overlays
- Level 5+ → scrims and modal backdrops

Interpretation characteristics:

- alpha is the primary control
- luminance and chroma are derived
- overlays are typically resolved relative to a surface via `over` or `under`

---

## Typing Rules

Level availability is enforced at the type system level.

Example capability map excerpt:

```ts
fill: {
  level: Level
}

lines: {
  level: Level
}

visualVocabulary: {
  level?: never
}

overlays: {
  level: Level
}
```

This ensures:

- autocomplete accuracy
- compile-time rejection of invalid combinations
- clear developer intent

---

## Explicit Non-Goals

The Level axis must never:

- be inferred automatically
- be derived from intent or state
- encode semantic meaning
- decide contrast direction
- replace emphasis or hierarchy

---

## Why Level Is Explicit

By forcing Level to be explicit:

- design decisions become auditable
- visual systems become stable over time
- refactors remain predictable
- tooling and documentation stay aligned

Level is a **declarative design decision**, not a heuristic.

---

## Example

```ts
const surface = resolve({
  usage: "fill",
  intent: "neutral",
  level: 1
})

const buttonFill = resolve({
  usage: "fill",
  intent: "brand",
  level: 4,
  on: surface
})

const buttonBorder = resolve({
  usage: "lines",
  intent: "brand",
  level: 5,
  on: buttonFill
})
```

Each level is explicit.
No inference occurs.
All behavior is explainable.

---

## Final Summary

The Level axis provides Palette Kit with:

- explicit spatial hierarchy
- Radix-compatible scaling
- predictable resolution behavior
- zero hidden heuristics

Level answers **where in the scale**, and nothing else.

This document defines the **Level axis contract** for Palette Kit v0.4.
