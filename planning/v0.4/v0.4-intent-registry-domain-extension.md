# Palette Kit v0.4 — Intent Registry & Domain Extension

## with Naming Best Practices

## Purpose

This document defines:

- where **custom intents** are declared
- how domains extend the Intent axis safely
- **naming rules** that preserve semantic clarity and system integrity

It exists to prevent semantic drift, axis mixing, and long‑term entropy.

---

## Core Principle

> **Intent names describe meaning, not appearance.**

An intent answers:
> *Why does this color exist in the product domain?*

It does **not** describe:

- where the color is used
- how strong it is
- what state it represents
- how it contrasts

---

## Intent Registry (Single Source of Truth)

All intents—core and domain-specific—are declared in a central registry
when creating the palette.

```ts
const palette = createPaletteKit({
  intents: {
    neutral: { hue: 0, chroma: 0 },

    income: { hue: 145, chroma: 0.14 },
    expense: { hue: 25, chroma: 0.16 },
    transfer: { hue: 250, chroma: 0.12 },
    investment: { hue: 285, chroma: 0.18 },
  }
})
```

This registry is:

- declarative
- immutable
- domain-owned
- required for resolution

The resolver only **references** this registry.

---

## What an Intent Name May Represent

Intent names may encode:

### 1. Domain Meaning

Examples:

- `income`
- `expense`
- `refund`
- `investment`
- `subscription`

### 2. Universal Semantic Meaning

Examples:

- `success`
- `danger`
- `warning`
- `info`

### 3. Brand Meaning

Examples:

- `brand`
- `accent`
- `highlight`

---

## What an Intent Name Must NEVER Encode

❌ Usage  

```ts
"textIncome"
"borderDanger"
"iconMuted"
```

❌ State  

```ts
"incomeHover"
"expenseDisabled"
```

❌ Level / Intensity  

```ts
"incomeStrong"
"dangerSubtle"
```

❌ Relation  

```ts
"textOnIncome"
"incomeOverlay"
```

These violate axis orthogonality and are explicitly disallowed.

---

## Naming Rules (Strict)

### Rule 1 — One Concept per Intent

Each intent must represent **exactly one semantic concept**.

Good:

- `income`
- `expense`

Bad:

- `incomePositive`
- `expenseNegative`

Sentiment belongs to **interpretation**, not naming.

---

### Rule 2 — No Visual Language

Intent names must not imply color appearance.

Bad:

- `green`
- `redAlert`
- `darkPrimary`

Good:

- `success`
- `danger`
- `brand`

---

### Rule 3 — Domain Language is Encouraged

Intent names should match the **language of the product domain**.

Finance:

- `income`
- `expense`
- `transfer`

Health:

- `critical`
- `stable`
- `recovery`

Education:

- `achievement`
- `warning`
- `focus`

Palette Kit does not normalize domains.

---

### Rule 4 — Flat Namespace

Avoid hierarchical or composite naming.

Bad:

```ts
"finance.income"
"income.primary"
```

Good:

```ts
"income"
```

Hierarchy belongs to documentation, not tokens.

---

## Intent Typing Strategy (Recommended)

```ts
type FinanceIntent =
  | "income"
  | "expense"
  | "transfer"
  | "investment"

const palette = createPaletteKit<FinanceIntent>({
  intents: { ... }
})
```

This ensures:

- compile-time validation
- no accidental typos
- explicit domain boundaries

---

## Error Handling Contract

Resolving an undefined intent must fail:

```ts
palette.resolve({
  usage: "fill",
  intent: "refund", // ❌ not registered
  level: 3
})
```

This is intentional and required.

---

## Why This Model Scales

Because:

- domains change
- products evolve
- meanings drift over time

By forcing explicit intent declaration:

- refactors are localized
- semantics stay auditable
- visual changes are safe

---

## Summary

- Intents live in the **Intent Registry**
- The registry is owned by the application domain
- Naming is semantic, not visual
- Orthogonality is preserved
- The resolver remains generic and deterministic

This document defines the **Intent Registry & Domain Extension contract**
for Palette Kit v0.4.
