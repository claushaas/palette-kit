# Palette Kit v0.4 — Contrast & Accessibility Contract

## Purpose

This document defines **exactly when and how Palette Kit enforces contrast and accessibility guarantees**.

Its goal is to:

- remove ambiguity about accessibility promises
- prevent false assumptions
- make contrast behavior explicit, testable, and auditable

Palette Kit does **not** promise universal accessibility.
It promises **deterministic accessibility where explicitly requested**.

---

## Core Principle

> **Contrast is enforced only when explicitly declared.**

In Palette Kit, accessibility is not implicit.
It is **opt-in via relation semantics**.

---

## The Role of Contrast in Palette Kit

Contrast exists for one purpose:

> **Ensure legibility of symbolic information.**

Contrast is therefore tied to:

- symbols
- reading
- interpretation

Not to:

- surfaces
- decoration
- depth
- branding

---

## When Contrast IS Enforced

Contrast enforcement happens **only** when:

```ts
on: target
```

is used.

This applies primarily to:

- `visualVocabulary` (text, icons, glyphs)
- `lines` when legibility is required

---

## When Contrast is NOT Enforced

Contrast is **never enforced** for:

- `fill`
- `overlays`
- `over`
- `under`

These usages communicate:

- space
- depth
- grouping
- emphasis

Not legibility.

---

## Contrast Algorithm (High-Level)

When `on` is present:

1. Resolver attempts to meet contrast by adjusting **L (luminance)**
2. If insufficient, **chroma is reduced**
3. Hue is **never changed**
4. Alpha is **never used** for text

This preserves semantic meaning while maximizing legibility.

---

## Perceptual Metrics

### Primary Metric: APCA

Palette Kit uses **APCA** as the primary contrast model when available.

Why APCA:

- perceptually uniform
- polarity-aware
- modern text contrast model

---

### Fallback: WCAG 2.x

WCAG contrast ratios are used:

- as a fallback
- for compatibility
- for tooling that requires numeric ratios

WCAG is never the primary decision driver.

---

## Contrast Targets (Indicative)

Palette Kit does not hardcode absolute values in the SPEC.
However, default targets follow these ranges:

| Content Type | Typical APCA Range |
| --- | --- |
| Body text | 60–75 |
| UI text | 45–60 |
| Icons / glyphs | 40–55 |

These values are:

- configurable
- preset-dependent
- never inferred

---

## Context Sensitivity

Contrast resolution is **context-aware**:

- light context → darker foregrounds
- dark context → lighter foregrounds

Directionality is derived from:

- background luminance
- environment context

Never from heuristics.

---

## Alpha & Accessibility

Rules are strict:

- Alpha is **forbidden** for `visualVocabulary`
- Alpha may be used for `lines` cautiously
- Alpha is primary for `overlays`

This prevents accidental contrast degradation.

---

## Failure Modes

If contrast cannot be satisfied:

- resolver fails explicitly
- or emits a warning (configurable)
- but never silently degrades

Example failure:

- extreme brand chroma
- insufficient luminance range

This is intentional.

---

## What Palette Kit Does NOT Guarantee

Palette Kit does not guarantee:

- full-page WCAG compliance
- accessibility without `on`
- contrast for decorative elements
- compliance without explicit intent

Accessibility is **declared, not assumed**.

---

## Testing & Verification

Recommended tests:

- Same input → same contrast output
- Changing output format does not change contrast
- Removing `on` removes contrast enforcement

Contrast behavior must be testable without UI rendering.

---

## Why This Contract Exists

Without an explicit contract:

- teams assume too much
- accessibility bugs hide silently
- systems overpromise and underdeliver

This document ensures:

- honesty
- predictability
- auditability

---

## Summary

- Contrast is **explicit**
- Enforcement is **opt-in**
- `on` is the accessibility switch
- Palette Kit never hides failures
- Responsibility is shared, not implied

This document defines the **Contrast & Accessibility Contract**
for Palette Kit v0.4.
