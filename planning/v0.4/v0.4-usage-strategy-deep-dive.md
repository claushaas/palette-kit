# Palette Kit v0.4 — Usage Strategy Deep Dive

## Purpose

This document explains **why each usage exists**, what perceptual role it plays,
and how it behaves inside the resolver.

This is a **maintenance and correctness document**.

If you change a usage strategy without understanding this document,
you are almost certainly breaking the system.

---

## What is a Usage Strategy?

A **usage** answers a single question:

> **Where is this color used in the interface?**

Usage determines:

- which perceptual channels are allowed to change
- which relations are valid
- what the color is *supposed* to communicate visually

Usage never defines:

- meaning (intent)
- importance (level)
- interaction (state)
- environment (context)

---

## Overview of Usages

| Usage | Role |
| ---- | ---- |
| fill | Surfaces and solid areas |
| visualVocabulary | Symbols that carry explicit meaning |
| lines | Separators, borders, outlines |
| overlays | Layering, depth, shadows |

Each usage has **non-overlapping responsibilities**.

---

## 1. fill

### Conceptual Role

`fill` represents **physical surfaces**.

Examples:

- cards
- panels
- buttons
- list items
- backgrounds

A fill color defines **where things exist**.

---

### Allowed Channels

- L (primary)
- C (secondary)
- H (from intent)
- α (allowed, but conservative)

---

### Level Interpretation

For `fill`, level maps to **surface depth / emphasis**.

- lower levels → closer to background
- higher levels → more prominent surfaces

Level is always required.

---

### Relation Compatibility

| Relation | Allowed | Reason |
| ---- | ---- | ---- |
| on | optional | content on surface |
| over | ❌ | surfaces are not overlays |
| under | ❌ | surfaces are not shadows |

---

### Common Patterns

```ts
// Card background
fill + level 1–2

// Primary action surface
fill + level 4–6
```

---

### Failure Modes

- using `fill` for text → wrong
- encoding importance in intent → wrong
- skipping level → invalid

---

## 2. visualVocabulary

### Conceptual Role

`visualVocabulary` represents **symbols that carry explicit meaning**.

Examples:

- text
- icons
- emojis
- glyphs

These elements must be **readable and unambiguous**.

---

### Allowed Channels

- H (from intent)
- L (contrast-driven only)
- C (may be reduced for contrast)
- α (❌ forbidden)

---

### Level Interpretation

Level is **forbidden**.

Symbols do not have depth.
They are evaluated purely by contrast.

---

### Relation Compatibility

| Relation | Allowed | Reason |
| ---- | ---- | ---- |
| on | required | legibility |
| over | ❌ | symbols are not layers |
| under | ❌ | symbols are not shadows |

---

### Common Patterns

```ts
// Text on surface
visualVocabulary + on

// Icon inheriting semantic color
visualVocabulary + intent + on
```

---

### Failure Modes

- using alpha for text → forbidden
- encoding hierarchy via level → wrong
- skipping on → unsafe

---

## 3. lines

### Conceptual Role

`lines` represent **structural separation**.

Examples:

- borders
- dividers
- outlines
- separators

Lines should be **visible but unobtrusive**.

---

### Allowed Channels

- L (compressed range)
- C (heavily reduced)
- H (usually inherited)
- α (preferred)

---

### Level Interpretation

For `lines`, level controls **subtlety**, not depth.

- low level → barely visible
- high level → stronger separation

---

### Relation Compatibility

| Relation | Allowed | Reason |
| ---- | ---- | ---- |
| on | optional | contrast against surface |
| over | ❌ | lines are not overlays |
| under | ❌ | lines are not shadows |

---

### Common Patterns

```ts
// Divider
lines + level 1–2

// Emphasized border
lines + level 3–4
```

---

### Failure Modes

- same chroma as fill → too loud
- using lines as decoration → misuse

---

## 4. overlays

### Conceptual Role

`overlays` represent **layers above or below surfaces**.

Examples:

- modals
- scrims
- shadows
- dimming layers

Overlays communicate **depth and separation**, not meaning.

---

### Allowed Channels

- α (primary)
- L (secondary)
- C (minimal)
- H (intent-driven, often neutral)

---

### Level Interpretation

For overlays, level controls **strength of effect**.

- low level → subtle
- high level → strong separation

---

### Relation Compatibility

| Relation | Allowed | Reason |
| ---- | ---- | ---- |
| on | ❌ | overlays do not carry content |
| over | ✅ | layering |
| under | ✅ | shadows |

---

### Common Patterns

```ts
// Scrim
overlays + over + level 2–3

// Shadow
overlays + under + level 1–2
```

Overlays may use any registered intent.
`neutral` is the common default for shadows and scrims.

---

### Failure Modes

- using overlays for branding → wrong
- enforcing contrast → wrong
- encoding meaning → misuse

---

### Why Usage Must Remain Strict

If usages blur:

- semantics leak
- accessibility breaks
- system becomes unpredictable

Usage strategies are **guardrails**, not preferences.

---

### Summary

Each usage exists to protect a specific perceptual role:

- fill → surfaces
- visualVocabulary → meaning
- lines → structure
- overlays → depth

If you are unsure which usage to pick,
the problem is in the design — not the API.

This document defines the **Usage Strategy Contract**
for Palette Kit v0.4.
